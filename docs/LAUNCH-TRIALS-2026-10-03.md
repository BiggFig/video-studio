# Three software launch films — 3 October 2026

The previous Obsidian export waited 8.73 seconds before showing its editable product workflow. A short action was followed by long static scenes, repeated orb staging, duplicate branding and a diagram that largely repeated the benefit. Passing source and integrity checks did not make that film compelling.

This batch tests three different software products with earlier demonstrations, compact source-supported workflows, distinct scene compositions and a purposeful instrumental pulse. The engine changes are reusable; any manually supplied evidence or authored recovery must be identified separately from automatic URL generation.

## Engine changes

- Research ranks workflows by visible before/after contrast and a concrete audience problem, while preserving the context needed to understand the result.
- Scripting avoids a mandatory standalone brand bumper and redundant benefit diagrams. Requested durations stay near the existing safe reading minimum; the advisory target is 20–24 seconds when the evidence allows it.
- Fresh shots use visual direction version 2: editorial typography, a restrained identity composition, a clean product stage and an action-led close. Retained version-1 films and their repairs preserve their original renderer contract.
- Wide captured logos no longer compete with a second large product-name heading in fresh brand scenes. Visible-asset reporting follows what is actually rendered.
- Music guidance asks for a tone-appropriate pulse, development and quiet space for the demonstration. It does not promise synchronization that the engine cannot guarantee.

Existing source, layout, claim, action/result, reading, budget and final-file quality gates remain required. No production beta allowance is reset for these local engine tests.

## Delivered creative direction

To fulfill the request for three actual films, the team authored three source-informed HTML/SVG compositions using the same pinned GSAP/Hyperframes rendering runtime. These are **art-directed engine films**, not automatic planner output or automatic acceptance passes. Their execution is intentionally separate from production jobs. The public gallery states this distinction.

- **Linear:** 24 seconds; engineers and product builders; request → send → draft pull request → review. A focused official agent-pane crop grounds the interface. Source text and the existing draft PR identify a particular illustrative example, with no claim of a real submitted task, merged code or measured speed.
- **Tally:** 24 seconds; founders and creators; a document-like form appears → email entry → Contact me → the official default thank-you. The form and thank-you are separate public sources, joined as an illustrative supported flow. Lemon paper staging, a closer input shot and a result-to-close transition replace the generic orb treatment.
- **Todoist:** 24 seconds; busy independent professionals; thought → Quick Add → recognized date and priority → the matching task in Inbox. An official desktop demonstration supplies coherent before/after evidence. The film does not combine the old mobile composer with an unrelated Today list.

The compositions live in `studies/launch-linear.ts`, `studies/launch-tally.ts` and `studies/launch-todoist.ts`. `scripts/render-launch-study.ts` generates deterministic browser frames, exports the picture, compares sampled encoded frames with their HTML originals, attaches a soundtrack, and checks the final file. No source screenshot or reference-video pixels are in the generated picture. UI geometry, typography and marks are authored approximations, not exact application code.

Each film has one newly generated 24-second instrumental from ElevenLabs, with a separate persisted request and provider ledger. No vocals or narration were requested. The final mix is normalized and checked for non-silent audio, duration and peak level; those measurements are not a listening review or a guarantee of musical beat synchronization.

Hash-verified local source packs were also prepared under `.local/launch-*-sourcepack-20261003`. They are source research artifacts; no source-assisted provider acceptance pass is claimed for them.

## Next automation work exposed by this test

1. Select an entire demonstrable workflow before UI reconstruction. Follow relevant public help/demo links when the homepage has only a teaser; do not confuse a configured dropdown with a completed result.
2. Keep platforms and task values consistent across source states. The Todoist official desktop demonstration is a better input than the homepage's mobile/desktop marketing composite.
3. Separate observed source strings from authored example content and bind the actual interactive confirmation control. A submitted request bubble is not a send button.
4. Give UI correction a realistic token envelope before paying for the initial document; a correction that cannot fit should be prevented.
5. Design explicit committed-item semantics for list results. The current text-only terminal gate rejects legitimate new task rows, but merely accepting all list items would also admit selection/filter demonstrations. No validator relaxation was shipped in this batch.
6. Turn the three authored compositions into bounded reusable motion patterns, then compare fresh automatic outputs against them. Stronger authored films alone do not establish that the automatic pipeline can produce this quality.
